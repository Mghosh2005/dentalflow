1. Executive Summary & Product Direction
DentalFlow is evolving from an operational dental clinic and patient communication tool into an integrated
healthcare platform. This evolution unifies two existing codebases:
Existing DentalFlow Platform: Practice management, patient self-registration, appointment scheduling, AI
receptionist call logs, follow-up automation, analytics, and a 3-section patient portal.
AI X-ray Analyser (Dobbe): Deep learning detection of dental caries and periapical lesions from standard and
DICOM radiographs using Roboflow computer vision models.
Shared Patient Intelligence Layer: The unified canonical patient foundation connecting all modules to a
single, immutable patient identity, cross-practice tenancy boundaries, and clinical workflows.

⚠️ Mandatory Scope Decision (Architecture PDF Alignment)
The Consultation Analyser has been permanently removed from the product roadmap. The platform will NOT record,
listen to, or synthesize ambient dentist-patient conversations into automated treatment reports due to speech-
recognition error risks, background clinic noise, and generative hallucination liabilities. Standard clinician-entered
consultation notes remain fully supported as structured EHR records.
2. Source Code Audit of Repositories
2.1 Existing DentalFlow Platform ( Mghosh2005/dentalflow )
Frontend Architecture: Built with React 19.2.8 and Vite 8.2.2. Uses Tailwind CSS v3.4.19, Lucide React icons,
and Recharts. Navigation is managed client-side in App.jsx  via state switching. Includes a dedicated 3-section

Appointments, Patients, Inbox, Follow-ups, Alerts, Practitioners, Analytics, AI Settings).

WAL mode (18 tables). Tables include practices , users , user_accounts , practitioners , patients ,
appointments , enquiries , follow_ups , follow_up_messages , message_templates , alerts , call_logs , and
treatment_plans .

Auth & Tenancy: JWT authentication with persistent secrets, rate-limiting (5 failed attempts = 15m lockout),
strict role separation ( staff  vs patient ). Currently hardcoded to single practice ( PRACTICE_ID = 1 ).
Storage Audit: Zero persistent image/file storage currently exists. Audio transcription takes JSON base64
payloads, creates temporary files, spawns Whisper, and deletes them immediately.
Deployment: Configured for Render Web Service ( render.yaml ). Express serves prebuilt static assets from
frontend/dist .
2.2 AI X-ray Analyser ( adityanandanx/dental-conditions-detection  — "Dobbe")
Frontend Architecture: Next.js 15.3.3 App Router, React 19, TypeScript, Tailwind CSS v4, shadcn/ui, Zustand,
TanStack Query. Uses dcmjs-imaging  for WASM DICOM previewing and react-dropzone .
Backend Architecture: FastAPI 0.115.12, Python 3.12+, managed via UV. Uses pydicom , gdcm  1.1 for DICOM
decompression, Pillow + NumPy for windowing and PNG conversion.
AI Inference Pipeline: Roboflow Serverless Inference SDK invoking model adr/6 . Detects cavity  and
periapical_lesion  with normalized bounding boxes and confidence scores.
Report Pipeline: LangChain + OpenAI gpt-4o-mini  for narrative report generation.
Persistence Reality: Completely stateless. Uploads are handled in temporary files and discarded. No
database, no user accounts, no patient linking, and no audit trails exist.
Clinical Defect: The existing pipeline automatically synthesizes clinical diagnoses and treatment suggestions
with GPT-4o-mini without clinician-in-the-loop validation, violating medical device standards.

6. Safe Patient-Matching and Duplicate Prevention
🚨 Patient Safety Hazard: Name-Only Matching Prohibited
Associating radiographs with a patient based solely on a patient name match represents a catastrophic clinical safety
risk. DentalFlow strictly prohibits single-attribute name matching.

8. Clinical Safety & Regulatory Governance
8.1 Separation of Potential vs. Confirmed Findings
Unconfirmed Status Invariant: Machine predictions are immutably labeled as potential  until a licensed
clinician submits an attestation.
Zero Automatic Treatment Generation: Under no circumstances does an unreviewed AI detection insert a
procedure into treatment_plans  or dispatch communications to a patient.
Complete Cryptographic Provenance: Every finding in a patient chart permanently records: Image SHA-256  $
ightarrow$ Model Version (adr/6)  $ ightarrow$ Raw Bounding Box Coordinates  $ ightarrow$ Attesting
Clinician ID & Timestamp .
8.2 HIPAA / GDPR Privacy Boundary
DICOM De-identification: Before any image is processed by third-party vision engines (Roboflow), all DICOM
header PHI (Name, DOB, MRN, Clinic Details) is stripped. The external API receives only raw pixel buffers
mapped to an ephemeral UUID.
Tenant Data Isolation: Parameterized queries enforce WHERE practice_id = ?  on all data access. Cross-
practice leakage is strictly blocked.
Audit Trails: Read and write operations on radiographic studies generate immutable records in audit_events .
9. User Experience & Navigation Architecture
The user experience is consolidated into a single application to eliminate disjointed portal switching:
Patient Directory & Profile (Extended): Patients.jsx  receives a new "Imaging & Radiographs" tab
displaying historical studies with review badges ( Pending Review , Confirmed , Normal ) and direct upload
triggers.
Clinical Imaging Workspace (New Page): Houses practice-wide unreviewed radiograph queues and an
interactive medical image viewer supporting pan, zoom, contrast windowing, condition overlay toggles,
confidence filtering, and a clinician review drawer.
Patient Portal (Preserved Intact): Remains strictly partitioned into 3 sections (My Portal, My Appointments,
My Treatment Plan). Renders only clinician-attested procedures.

11. Recommended First Development Milestone
🎯 Milestone 1: "Shared Patient Intelligence Foundation" (Phases 2 & 3)
Primary Deliverable: Canonical Patient Identity, Schema Backfill, Patient Service, and Timeline API.
Why Milestone 1 Must Precede All Other Work
1. Prevents Duplicate Identities: Integrating an image analyzer before establishing a canonical patient model
leads to duplicate, fractured patient accounts that require complex manual reconciliation later.
2. Provides Immediate Operational Value: Creating the longitudinal timeline enriches existing scheduling,
follow-ups, and patient charts immediately, with zero clinical safety risks.
3. Guarantees Zero Regressions: Additive migrations ensure existing production operations on Render continue
uninterrupted.
Sprint 1 Task Backlog
1. Implement additive migrations in backend/src/db.js  ( canonical_uuid , medical_record_number ,
allergies_json , matching_status ).
2. Execute deterministic migration backfill script for existing patient records.
3. Build backend/src/services/patient-service.js  with multi-tier matching.
4. Implement in-process domain event bus ( backend/src/events/event-bus.js ).
5. Deploy GET /api/v1/patients/:id/timeline  endpoint.
6. Run regression suite test_verification_suite.mjs  to verify 100% operational integrity.
